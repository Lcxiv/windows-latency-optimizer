The case

"My computer froze
on the last boot."

What was claimed

A boot failure. User points at startup.

What happened

An idle hard-hang at 10:19 — mid-session, hours after a clean boot. Not boot at all.

Root cause

nvlddmkm GPU-driver DPC stalled the watchdog. Confirmed by decoding the dump, then verified the P0 fix held.

eventlog + WinDbg + nvidia-smi + pnputil + 90 days of memory → one verdict.

Two products in one trenchcoat

You've been building pull.
Every war story is push.

PULL — the curious operator

Monitor dashboard, audit, experiment archive. You go look when calm and bored. Built. Polished. Rarely the thing that cracks a case.

PUSH — the incident responder

Dead machine, need a verdict now. 4/23 · 5/11 · 5/20 · 5/30 — every real incident. Had no home in the app.

Decision made: build toward B — the installed sentinel that catches the pattern over months.

Kill the comforting lie

The moat is not decoding dumps.

WhoCrashed, BlueScreenView, NirSoft — they've run !analyze and printed the faulting module for 15 years. "Decode the dump for normies" is a 2010 product.

They see one file

You reconstructed the freeze from the sibling dump — because the freeze left no body.

They see one moment

You connected 04-11 → 05-11 → 05-30 as one nvlddmkm family across months.

They stop at the verdict

You decoded → fixed → verified P0 held 12/12. The loop, not the snapshot.

The real moat

Judgment over a broad
instrument ensemble.

Two things, together, that no commodity tool has:

① The judgment layer

Symptom-truth > config-truth. Per-CPU > _Total. Reconstruct from siblings when the body's missing. Absence is evidence. Today this was literally the model reasoning in context.

② The instrument breadth

A sensor for every layer — CPU/DPC, GPU/frametime, storage, network/WiFi, firmware, thermals. Few tools span all of it. WPR · xperf · CapFrameX · Wireshark · nvidia-smi · ProcMon · HWiNFO · SCEWIN

The strength is breadth. The weakness is they don't talk to each other.

The blunt diagnosis
You don't have an ensemble.
You have a pile.

145 scripts, 8 views, 41 checks — each emits its own format, into its own file, read by a human who holds the correlation in their head.

"Tools don't work together" and "analysis isn't there yet" are the same problem: there's no shared substrate for analysis to run on. Analysis can't see across tools that don't speak a common language.

The keystone

Build the evidence bus first.

One typed, timestamped, append-only timeline. Every instrument writes findings as rows. Correlation stops being your brain and becomes a query.

// one row = one observation from one instrument at one instant { ts, source, subsystem, signal, severity, value, faulting_module, cpu, confidence, evidence_kind: "observed" | "inferred" | "absent", raw_ref, incident_id, links:[row_id] }

evidence_kind has three states — because the 6-min logging silence was the most diagnostic fact in the case. Absence must be storable.

Proof on paper

05-30 + 05-11 as rows.
The hard cases hold.

// 05-11 — dump exists { signal:"dpc_watchdog", faulting_module:"nvlddmkm", evidence_kind:"observed", raw_ref:"dump_0x133...", id:"a2" } // 05-30 — NO dump. absence + inference-by-link { signal:"log_silence", evidence_kind:"absent", value:{duration_s:349} } { signal:"dirty_shutdown", value:{kp41_bugcheck:0}, evidence_kind:"observed" } { signal:"dpc_watchdog_hang", evidence_kind:"inferred", confidence:0.7, faulting_module:"nvlddmkm", links:["a2"] }

Cross-month join = GROUP BY faulting_module → nvlddmkm × 3. The pattern is now a query, not a memory.

Two traps on the road to B

Where expert tools
go to die.

① Liability for strangers' machines

Today's fixes wrote CrashControl, deleted a driver, flipped power modes. On your rig: fine. On a stranger's: "the app killed my display." Split read from write — verdict for all, remediation gated & reversible.

② Your data is n = 1

Every pattern is your 9800X3D + 5070 Ti. The cross-time correlator — your best feature — is worth nothing on day one for a new user. Cold-start is real.

Riskiest assumption — and the cheap test

Is the signal vocabulary
small & stable?

The bus only stabilizes if the diagnostic vocabulary is finite. Union across the last 6 RCAs:

dpc_watchdogdirty_shutdowncpu0_dpc pstate_samplewhea_errorlog_silence driverstore_statestorport_perfhypervisor/vbs kernel_power_109ping_rtt/jittergpu_util minifilter_altlink_dropbios_settingframetime_hitch

~16 types, ~9 subsystems, the recurring few are the spine of nearly every case. Under the 20 threshold → assumption holds → safe to build.

Where this lands

The product, restated.

LatencyGuard isn't a PowerShell app with an LLM bolted on. It's a broad Windows-forensics collector + a reasoning layer + a verdict UI.

The 145 scripts are the moat as a sensor array, not as a diagnostician. The instruments give breadth across every layer; the bus makes them speak one language; the reasoning layer does — reproducibly — what took a human-plus-model an hour today.
